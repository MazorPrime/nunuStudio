Yes. We can build a **browser-based 3D game creation studio inspired by Sorceress**, but I would not try to clone the entire site in one shot.

Sorceress currently combines several separate products: AI image generation, image-to-3D, automatic rigging/weight painting, text-to-animation, GLB/FBX/GLTF export, voxel tools, audio, materials, and an AI-driven game engine/editor. ([Sorceress][1]) The smartest version for you would start with the **actual 3D game-building environment**, then bolt the AI generators onto it.

### What I would build

Think of it as:

**Mazpon 3D Studio**

```text
┌───────────────────────────────────────────────────────────────┐
│ MAZPON 3D STUDIO        Project ▼     ▶ PLAY      SAVE       │
├──────────────┬────────────────────────────────┬───────────────┤
│ ASSETS       │                                │ INSPECTOR     │
│              │                                │               │
│ Characters   │          3D VIEWPORT           │ Transform     │
│ Creatures    │                                │ Position      │
│ Buildings    │        [Actual Game World]     │ Rotation      │
│ Terrain      │                                │ Scale         │
│ FX           │                                │               │
│ Audio        │                                │ Material      │
│ Scripts      │                                │ Physics       │
│              │                                │ Behavior      │
├──────────────┴────────────────────────────────┴───────────────┤
│ SCENE │ World > Dungeon > Room > Orc > Sword                 │
├───────────────────────────────────────────────────────────────┤
│ AI: "Make this creature patrol the room and attack enemies"  │
│                                                     [BUILD]   │
└───────────────────────────────────────────────────────────────┘
```

The foundation fits extremely well with the web technology you're already using. **React Three Fiber** provides a React renderer for Three.js, and Three.js provides the actual 3D rendering, cameras, controls, animation and WebGL/WebGPU layer. ([Poimandres Documentation][2]) For physics I'd use **Rapier**, which already integrates with React Three Fiber. ([PMNDRS][3])

And Supabase can handle project saves, accounts, asset metadata and eventually collaborative editing or multiplayer because its current Realtime system provides Broadcast and Presence. ([Supabase][4])

## AI would sit on top of the editor

Instead of AI generating random disconnected files, it would understand the studio.

You could type:

> Create a dungeon room with four stone walls, a wooden door and two torches.

And it could create actual scene objects.

Then:

> Make the door open when the player gets within five feet.

It creates a trigger and behavior.

Then:

> Put three goblins inside. They should patrol until they see the player.

It creates instances and attaches AI/behavior components.

Then:

> Goblins have 40 health, do 8 damage and drop between 2 and 6 gold.

Those become editable component properties.

So you'd still have a **real editable game underneath the AI**, instead of a black box.

That's an important distinction.

```text
Next.js / React
       │
       ├── Studio UI
       │
       ├── React Three Fiber
       │       │
       │       └── Three.js
       │
       ├── Rapier Physics
       │
       ├── Game Runtime
       │
       ├── Component System
       │
       ├── Asset Manager
       │
       └── AI Agent
                │
       ┌────────┼─────────┐
       ▼        ▼         ▼
   Coding AI  Image AI   3D AI

                 │
                 ▼
              Supabase
        ┌────────┼────────┐
        ▼        ▼        ▼
      Auth    Projects   Assets
```

This approach doesn't fight your existing web stack; it extends it. React Three Fiber is explicitly built for declarative Three.js scenes, and its event system supports pointer/click interactions with objects, which is exactly what an editor needs. ([Poimandres Documentation][2])

## How I'd Build It

I would divide it into roughly these stages:

**Phase 1 — Editor Core**

3D viewport, objects, hierarchy, inspector, transforms, asset loading, save/load.

**Phase 2 — Game Runtime**

Play mode, components, scripts, collisions, physics, triggers, animation.

**Phase 3 — World Building**

Terrain, prefab system, lights, environment, particle systems, navigation and AI.

**Phase 4 — AI Game Builder**

Something like:

> Add a stone bridge across this river.

> Make that dragon hostile.

> Create a health potion.

> Change these enemies to ranged attackers.

**Phase 5 — AI Asset Studio**

Prompt/image → 3D → rig → animation → asset library.

**Phase 6 — Full Game Packaging**

Project export, hosted web games, versioning and share links.

**Phase 7 — Multiplayer/Collaboration**

Shared project editing, multiplayer runtime and testing rooms.

Supabase Presence/Broadcast could later support the collaborative portions. ([Supabase][4])

### One thing I would *not* do

I would **not start by attempting Sorceress's entire asset-generation suite**.

That would mean building image generation, video generation, sound generation, voxel generation, rigging, animation, material generation, sprite tools and a game engine simultaneously. Sorceress itself currently presents those as many separate tools/modules. ([Sorceress][1])

I'd build the **actual game studio first**.

Once it can create a scene like:

> floor → walls → player → creature → lights → physics → AI → combat → playable

we have something valuable.

Then every AI generator we add makes that studio more powerful.

And yes, **this is absolutely something I could help you implement incrementally in your repo**, rather than merely design conceptually. Given your existing Next.js/Supabase setup, I'd strongly favor adding it as something like **`/studio`** and building the first functional viewport/editor there.
